## 3. ELO 측정 방식

### 3.1 v1 해체

```
초기값      R₀ = 1500 + 200 · Φ⁻¹(P_mid),  P_mid = {T1: 0.95, T2: 0.70, T3: 0.25} → 1829 / 1605 / 1365
K           비교 ≤15회 48, ≤40회 24, 이후 12
            단, |R − 1700| < 100 또는 |R − 1500| < 100 이면 K = 60
갱신        R′ = R + K (S − E),  E = 1 / (1 + 10^((R_b − R_a)/400))
안정도      1 − (최근 20회 평균 |ΔR|) / 50
```

1. **K가 줄지 않는다.** 두 "경계" 구간의 합집합이 (1400, 1800)이다. T2의 시작점 1605가 이 안에 있고, T1(1829)·T3(1365)도 몇 번만 움직이면 들어온다. 결과적으로 **대부분의 곡이 비교 횟수와 무관하게 K=60**으로 움직이며, 레이팅이 수렴하지 않는다.
2. **"정렬 안정도"는 순위 품질을 재지 못한다.** 이 값은 최근 레이팅 변화량, 즉 사실상 K의 크기를 잰다. 시뮬레이션(300곡)에서 실제 쌍 순서 정확도가 75% → 88%로 오르는 동안 안정도는 66~72%에 머물렀고, 중간에 **내려가기도** 했다. "80% 이상이면 충분히 수렴"이라는 안내는 사실상 도달하지 않는다.
3. **Elo의 구조적 한계.** 같은 비교 결과라도 입력 순서에 따라 최종 레이팅이 달라지고, A가 B를 이긴 뒤 B가 강해져도 A는 그 공을 소급해 받지 못한다. 곡당 비교가 몇 번뿐인 이 앱의 사용 패턴에서 특히 불리하다.
4. 불확실성을 표현하지 않아 "이 곡의 순위를 얼마나 믿어도 되는지"를 알 수 없다.

### 3.2 v2: 베이지안 Bradley–Terry

각 곡의 숨은 취향 강도 θ(자연로그 오즈)에 대해

```
P(a가 b보다 좋다) = σ(θa − θb)                     σ: 로지스틱 함수
θi ~ N(μi, vi)                                       티어 사전분포 (4장)
θ̂ = argmin  Σi (θi − μi)² / 2vi
           − Σ(a,b,s) [ s·log σ(θa−θb) + (1−s)·log σ(θb−θa) ]
```

- 응답 점수 s ∈ {1, 0.75, 0.5, 0.25, 0}을 그대로 부분 승리로 반영한다.
- 해법: 좌표별 뉴턴 스윕. 곡률을 `max(h, h_upper/2)`로 잡아 매 스텝 목적함수 감소를 보장하고(`h_upper = 1/v + 차수/4`), 직전 해에서 출발한다.
- 불확실성: 라플라스 근사의 대각 성분 `σi² ≈ 1 / (1/vi + Σ p(1−p))`.
- 화면·저장은 익숙한 Elo 척도 그대로(`R = 1500 + θ · 400/ln10`, 400점 = 오즈 10배).

이 방식으로 얻는 성질 (모두 단위 테스트로 확인):
- **비교 순서와 무관**하다. 모든 비교를 한꺼번에 푸는 전역 추정이다.
- **되돌리기가 정확하다.** 기록에서 비교 한 건을 빼고 다시 풀면 이전 값과 같아진다(v1은 스냅숏 복원).
- **티어 경계를 넘는다.** T3 곡이 T2 곡들을 계속 이기면 순위가 역전된다.
- 곡마다 **±σ(불확실성)** 가 있어 랭킹에 표시하고, 다음 쌍 선택에 쓴다.

### 3.3 예상 정확도

```
예상 정확도 = 임의의 두 곡 (i, j)에 대해 P(현재 순서가 맞음)의 평균
            = mean Φ( |μi − μj| / √(σi² + σj²) )
```

50%는 무작위, 100%는 완전히 확정된 순서다. 곡 수와 무관하게 해석되고, 쌍이 많으면 고정 시드로 3만 쌍을 표본 추출해 계산량을 일정하게 둔다. 티어 분류만으로 보통 75% 안팎에서 시작한다.

## 4. 티어 분류

### 사전분포: 고정 비율 → 실제 비율 + 직감 잡음

사용자가 곡의 실제 취향 x에 잡음 ε ~ N(0, τ²)이 섞인 직감 y = x + ε로 티어를 고르고, 티어 비율대로 y의 분위 구간을 나눈다고 모델링하면

```
E[x | tier]   = m′ / √(1+τ²)
Var[x | tier] = (τ² + v′) / (1+τ²)          m′, v′: 해당 분위 구간으로 자른 표준정규의 평균·분산
```

τ = 0.5(직감이 꽤 일관적인 사용자)를 기본값으로 쓴다. 분류 초반에 비율이 튀지 않도록 권장 비율(10/40/50)을 의사 표본 10곡만큼 섞는다.

| 실제 분류 비율 | T1 | T2 | T3 |
|---|---|---|---|
| v1 (항상 고정) | 1829 | 1605 | 1365 |
| 10/40/50 | 1814 ± 116 | 1600 ± 110 | 1357 ± 140 |
| 30/40/30 | 1708 ± 128 | 1501 ± 104 | 1293 ± 128 |
| 5/25/70 | 1868 ± 111 | 1674 ± 105 | 1411 ± 154 |

권장 비율로 분류하면 v1과 거의 같은 값이 나오지만, Tier 1을 30%로 잡는 사용자에게 v1은 "T1 = 상위 5% 지점"이라는 틀린 가정을 적용했다. v2에서 권장 비율은 **가이드일 뿐**이고, 화면에도 그렇게 안내한다.

### 분류 화면

- 키 반복 방지, 모달 뒤 입력 차단. 자동 재생은 곡에 1초 머물러야 요청하고, 재생 요청은 한 번에 하나만 보내 가장 최근 곡만 재생한다. 429·5xx 뒤에는 곡을 넘겨도 대기 시간 동안 아무것도 보내지 않는다(`player/playQueue.ts`). 처음의 250ms 디바운스만으로는 빠르게 넘길 때 지나간 곡의 요청이 겹쳐 순서가 뒤바뀌거나, 429 재시도가 요청 제한을 붙잡아 지금 곡이 재생되지 않았다.
- "남은 곡 모두 Tier 3"은 확인창 + **한 묶음으로 되돌리기 가능**(v1은 되돌릴 수 없었음).
- 휴대폰: 진행률 → 앨범 아트 → 곡 정보 → 티어 버튼(3열) 순으로 쌓고, 앨범 아트가 남는 공간에 맞춰 커지고 줄어들어 **스크롤 없이 분류**. 데스크톱은 2열(아트 | 정보·버튼) + 세로 공간이 넉넉하면 다음 곡 미리보기.
- 분류 현황: 티어 버튼마다 지금까지의 비율과 권장 비율을 함께 표시. 다만 "억지로 맞출 필요 없다"고 명시.
- 티어 변경은 랭킹 화면의 각 행에서. 바꾸면 그 곡의 사전분포가 새 티어로 바뀌고 레이팅이 재계산된다.

## 5. 비교 정렬 (다음 쌍 선택과 응답)

### v1

A = 비교 횟수가 가장 적은 곡 중 무작위, B = **같은 티어** 안에서 아직 안 본 쌍 중 레이팅이 가까운 5곡 중 무작위. 티어라는 벽 때문에 T2 상위권과 T1 하위권의 순서는 끝까지 비교되지 않고 사전 점수로만 정해졌다.

### v2

- **A**: 티어 사전분포 대비 불확실성(σ / σ_tier)이 가장 큰 곡들 중 무작위. 비교가 적은 곡, 새로 들어온 곡, (v1에서 옮겨와 이미 정보가 있는 곡보다) 모르는 곡이 먼저 나온다.
- **B**: A와 레이팅이 가까운 24곡 중, 이미 본 쌍은 가능하면 피하고 **결과를 가장 예측하기 어려운**(p(1−p) 최대, p는 σ를 반영한 예측 승률) 상위 3곡 중 무작위. 티어와 무관하다.
- 좌우 배치는 무작위(위치 편향 제거). 직전 쌍의 곡은 가능하면 다시 내지 않는다.
- **상위권 집중 모드**: A를 현재 상위 15%(최소 10곡)에서만 뽑는다.

시뮬레이션에서 B 선택 규칙(최근접 5곡 무작위, p(1−p), 분산 감소량 최대화 등)끼리의 전체 정확도 차이는 ±0.4%p로 **오차 범위 안**이었다. 그래서 가장 설명하기 쉬운 p(1−p)를 택했다. 반면 상위권 집중 모드는 Top 10 적중률을 크게 바꾼다(8장).

### 응답 방식

| 키 | 의미 | 점수 |
|---|---|---|
| `1` · `←` · A 앨범 아트 클릭 | A 확실히 | 1 |
| `2` | A 조금 더 | 0.75 |
| `3` · `↓` | 비슷함 | 0.5 |
| `4` | B 조금 더 | 0.25 |
| `5` · `→` · B 앨범 아트 클릭 | B 확실히 | 0 |
| `S` | 건너뛰기 (기록 안 함, 모르는 곡일 때) | — |
| `Z` | 되돌리기 (같은 쌍을 같은 배치로 다시 보여줌) | — |
| `A` / `B` / `Space` | A 재생 / B 재생 / 재생·일시정지 | — |

- 버튼 배치와 키 의미가 **항상 같다.** v1은 점수 차 150을 기준으로 3개/5개 버튼이 바뀌며 레이아웃이 흔들리고 키 의미도 바뀌었다.
- "두 곡 점수가 비슷해 세밀한 비교를 요청합니다" 같은 문구를 없앴다. 판단 전에 점수 정보를 주면 판단이 거기에 끌려간다(앵커링).
- 직전 비교 결과를 한 줄로 보여 주어 실수를 바로 알아채고 되돌릴 수 있다.

## 6. 랭킹

- 분류된 곡만 레이팅순. 동점이면 더 확실한(σ가 작은) 곡 먼저.
- 검색(제목·아티스트·앨범), 티어 필터, 행마다 티어 변경.
- 레이팅 옆 **±σ**, 비교 횟수. "분류한 티어"와 "현재 순위가 속한 구간"(티어별 곡 수로 위에서부터 자른 구간)이 다르면 ↑/↓ 표시 — 재분류 후보를 보여준다(자동으로 바꾸지는 않는다: 사후분포로 사전분포를 고치면 같은 증거를 두 번 세게 된다).
- 예상 정확도 막대. 곡 행의 앨범 아트를 누르면 바로 재생/일시정지(데스크톱, 재생 중인 곡은 순위 자리에 이퀄라이저), 재생할 수 없으면(휴대폰 등) 앨범 아트가 Spotify 링크. 행 끝의 링크로도 Spotify에서 열 수 있다.
- CSV: 순위·제목·아티스트·앨범·티어·레이팅·불확실성·비교 수·Spotify URL, UTF-8 BOM.

## 7. 저장 · 동기화

- **저장 형식 v2**: `{ version: 2, ownerId, source, sourceName, tracks, matches, compCount, legacySeen, lastSyncedAt, savedAt, syncedAt }`. 비교 기록(matches)이 원본이고 레이팅·σ는 파생값이다.
- **v1 자동 마이그레이션**: v1은 비교 기록 없이 곡별 레이팅만 남겼다. 비교한 곡은 "v1 초기값 대비 오프셋 + 비교 횟수만큼 좁아진 σ(정보량을 절반으로 할인)"의 곡별 사전분포로 옮겨 **기존 순위를 유지**한다(테스트 픽스처와 브라우저 E2E 모두 v1 순서와 일치). 원본은 `eloState.v1-backup`에 한 번 보관한다. localStorage 키(`eloState`), Spotify 토큰 키는 그대로라 업데이트 후에도 로그인·세션이 유지된다.
- **검증**: localStorage·Supabase·백업 파일 어디서 온 데이터든 `parseSession`이 필드를 검사하고, 깨진 트랙·중복·존재하지 않는 곡을 가리키는 비교 기록을 걸러낸다.
- **클라우드**: 변경 10건이 쌓이면 즉시, 아니면 마지막 변경 15초 뒤 업로드. 실패하면 30초 뒤 재시도. 사이드바(좁은 화면은 상단 바)에 단일 저장 상태 표시(v1은 단계마다 "미저장 N곡/N회"를 따로 셌다). 요약(`data->summary`)만 받아 클라우드 상태를 확인해 수 MB짜리 전체 데이터를 매번 내려받지 않는다.
- **충돌**: 세션마다 마지막으로 맞춘 클라우드 버전(`syncedAt`)을 기록한다. 클라우드의 `savedAt`이 다르고 진행 정도도 다르면 다른 기기에서 저장한 것으로 보고 자동 업로드를 멈춘 뒤 "클라우드 버전 불러오기 / 이 기기 버전으로 덮어쓰기"를 묻는다.
- **백업 파일**: Supabase 없이도 JSON으로 내보내기/불러오기.
- 로그아웃해도 로컬 세션은 남고, 로그인 없이도 비교·랭킹은 계속할 수 있다(재생만 불가).

`bench/`는 가상의 사용자로 전략을 비교한다.

- 곡의 실제 취향 θ ~ N(0, 200²) (Elo 단위)

### 해석

- 전체 정확도에서 v2의 이득은 작다(0.5~1.7%p). 곡당 비교가 몇 번뿐인 구간에서는 어떤 모델이든 "티어 사전분포 + 몇 번의 비교"에 좌우되기 때문이다. 이득은 직감이 부정확할수록 커진다.
- "경계 K=60"은 초반 정확도에는 거의 영향이 없었다(±0.3%p). 문제는 정확도가 아니라 **수렴을 막아 안정도 지표를 무의미하게 만든 것**이었다.
- 순위에서 사람들이 가장 신경 쓰는 상위권은 **상위권 집중 모드**로 훨씬 빨리 확정된다. 대신 전체 정확도는 낮아지므로 선택 사항으로 두었다.
- Top 10 수치는 시드 수가 적어 ±5%p 정도의 흔들림이 있다. 상위권 집중 모드의 차이(+15~25%p)는 그보다 훨씬 크다.

`npm run bench`(빠른 버전, CI 포함)는 다음 세 가지를 회귀 조건으로 검사한다: v2 정확도 ≥ v1 − 1%p, 표시값과 실제 정확도 차이 < 3%p, 상위권 집중 모드의 Top 10 ≥ 기본 모드.

## 9. UI/UX · 접근성

- **반응형**: 넓은 화면은 왼쪽 사이드바, 좁은 화면은 상단 바 + 하단 탭 바. 불러오기·분류·비교 화면은 가로를 꽉 채우고 한 화면에 맞춰 페이지 스크롤이 없다(앨범 아트가 남는 공간에 맞춰 크기 조절, 긴 목록만 안에서 스크롤). 랭킹만 세로로 스크롤한다. 창이 너무 낮으면 잘리지 않고 스크롤된다.
- **일관된 디자인 토큰**: Apple Music 풍 색상(흰색/짙은 회색 바탕, 회색 채움, 키 컬러 빨강 하나)을 CSS 변수 → Tailwind v4 `@theme`으로 노출(`bg-section`, `text-fg-2` …). 버튼·세그먼트 컨트롤·모달·확인창·진행 막대를 공용 컴포넌트로.
- **명암비**: 모든 본문/배경 조합을 WCAG AA(4.5:1) 이상으로 조정. v1은 다크 테마 보조 텍스트가 2.9:1, 라이트 테마의 강조색 글자가 2.4:1이었다.
- **확인창**: 세션 삭제, 새 세션 시작, 클라우드 덮어쓰기/불러오기/삭제, 일괄 분류 전. 네이티브 `<dialog>`라 포커스 가두기·Esc·배경 비활성화가 브라우저 수준에서 보장된다.
- 한글 줄바꿈(`word-break: keep-all`), iOS 홈 화면 앱의 상태 표시줄·홈 표시줄 영역(safe-area), 모션 감소 설정 존중, 건너뛰기 링크, ARIA(progressbar/meter/radiogroup, `aria-keyshortcuts`).
- **재생**: Premium이 아니거나 SDK를 쓸 수 없으면 이유를 알려 주고 Spotify 임베드 플레이어로 대체(v1은 비교 화면에서 "전곡 재생 불가"만 표시). 브라우저 자동 재생 정책에 맞춰 첫 입력 때 오디오를 활성화.
- 오류 화면에서 저장 데이터를 바로 내려받을 수 있다.

## 11. 남은 과제

- **Spotify 플레이리스트로 내보내기**(상위 N곡): `playlist-modify-*` 스코프가 필요해 기존 사용자는 다시 로그인해야 한다.
- **Supabase Auth + RLS**: 지금은 anon key로 직접 쓰므로 URL과 키를 아는 사람은 모든 행을 쓸 수 있다(README 참고).
- **τ(직감 잡음) 개인화**: 비교 결과와 티어가 얼마나 어긋나는지로 사용자별 τ를 추정하면 초반 예상 정확도의 낙관 편향(8장)을 줄일 수 있다.
- **시간 감쇠**: 오래전 비교의 가중치를 낮춰 취향 변화를 반영.
- **오프라인**: Service Worker가 없어 설치형 앱도 오프라인에서는 열리지 않는다.
